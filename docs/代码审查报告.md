### 1. `assert_audit_log_append_only` 使用字典深度相等比较 — `backend/auto_voucher/database.py:311`

```python
if item_id not in incoming_by_id or incoming_by_id[item_id] != item:
    raise ValueError("审计日志只允许追加，不能修改或删除已有记录")
```

**问题**: 字典的 `!=` 比较是深度相等而非引用相等。如果 `incoming` 中某条记录与 `existing` 中对应 ID 的记录在**所有字段上完全相同**，比较返回 `False`（视为"未修改"），允许通过。

**风险分析**: 在实际审计日志中几乎不会发生，因为每条记录有唯一 ID 和时间戳。但如果攻击者构造两条具有相同时间戳、相同操作者、相同内容的记录，第二条可能替换第一条而不被检测。

**建议修复**:
```python
# 比较序列化后的哈希而非原始 dict
import json
existing_hashes = {item["id"]: hashlib.sha256(
    json.dumps(item, sort_keys=True).encode()
).hexdigest() for item in existing}
# ... 然后用哈希比较
```

### 2. `handle_one_request` 在异常后可能发送两次 HTTP 响应 — `backend/auto_voucher/server.py:228-251`

```python
def handle_one_request(self) -> None:
    try:
        super().handle_one_request()
    except Exception as exc:
        # ... 诊断日志 ...
        try:
            self.json_response({"error": "..."}, HTTPStatus.INTERNAL_SERVER_ERROR)
        except Exception:
            pass
```

**问题**: 如果 `super().handle_one_request()` 已经发送了 HTTP 状态行和部分响应头，在写入 body 之前抛出异常，这里的 `json_response` 会尝试发送第二个完整 HTTP 响应，导致协议错误。客户端可能收到损坏的响应。

**建议修复**:
```python
def handle_one_request(self) -> None:
    self._response_sent = False
    try:
        super().handle_one_request()
        self._response_sent = True
    except Exception as exc:
        if not getattr(self, '_response_sent', False):
            try:
                self.json_response({"error": "..."}, HTTPStatus.INTERNAL_SERVER_ERROR)
            except Exception:
                pass
```

### 3. `saveState` 静默吞下持久化错误 — `src/store.js:67-78`

```javascript
saveQueue = saveQueue
    .catch(() => undefined)   // <-- 吞下错误，队列继续
    .then(() => apiRequest("/api/state", {
      method: "PUT",
      body: JSON.stringify({ state: snapshot }),
    }))
    .catch((error) => {
      window.dispatchEvent(new CustomEvent("auto-voucher:sync-error", { detail: error.message }));
    });
```

**问题**: `.catch(() => undefined)` 将前一次 save 的错误完全吞没。之后 `.then()` 继续执行时，**被吞掉的错误的 save 对应的 state 不会重试**。如果用户快速连续操作，中间某次 save 失败后，后续 save 可能覆盖掉中间的状态变更，导致数据丢失。

**建议修复**:
```javascript
let pendingRetry = null;

async function enqueueSave(state) {
  const snapshot = JSON.parse(JSON.stringify(state));
  saveQueue = saveQueue
    .catch((error) => {
      // 将失败的状态放入重试队列而非直接吞掉
      if (!pendingRetry) pendingRetry = snapshot;
      throw error;
    })
    .then(() => apiRequest("/api/state", {
      method: "PUT",
      body: JSON.stringify({ state: pendingRetry || snapshot }),
    }))
    .then(() => { pendingRetry = null; })
    .catch((error) => {
      window.dispatchEvent(new CustomEvent("auto-voucher:sync-error", { detail: error.message }));
      throw error; // 保持链式失败，不吞错误
    });
}
```

### 4. 前端 `eventFromRow` 与后端 `event_from_row` 算法不一致 — `src/domain.js:75-107` vs `backend/auto_voucher/importers.py:174-255`

### 6. `restore_backup` 中路径遍历防护有边界情况 — `backend/auto_voucher/server.py:890-892`

```python
target = (root / name).resolve()
if root.resolve() not in target.parents:
    raise ValueError("备份包含不安全路径")
```

**问题**: 检查 `root` 是否在 `target.parents` 中——但如果 `name = "."`，`target == root`，而 `root.resolve()` 不在自身的 `parents` 中。这种情况下 `restore_backup` 会拒绝完全合法的路径。此外，zip slip 中如果 `name = "archive"` (恰好是目录名)，也会被误拒绝。

**建议修复**:
```python
target = (root / name).resolve()
if target != root.resolve() and root.resolve() not in target.parents:
    raise ValueError("备份包含不安全路径")
```

### 7. `DiagnosticLogger.prune()` SQL `LIMIT -1 OFFSET` 兼容性 — `backend/auto_voucher/diagnostics.py:306-316`

```sql
DELETE FROM diagnostic_log WHERE id IN (
    SELECT id FROM diagnostic_log
    ORDER BY occurred_at DESC
    LIMIT -1 OFFSET ?
)
```

**问题**: SQLite 文档说明 `LIMIT -1` 表示"无限制"，但在某些旧版本中行为可能不一致。此外，这种 `LIMIT -1 OFFSET N` 模式在大数据量下效率较低（需要扫描所有行来计算 offset）。

**建议修复**:
```sql
DELETE FROM diagnostic_log
WHERE id NOT IN (
    SELECT id FROM diagnostic_log
    ORDER BY occurred_at DESC
    LIMIT ?
)
```

然后在 Python 中将 `maxEntries` 作为 LIMIT 值传入。

### 10. `JobManager` 使用 daemon 线程，无优雅关闭 — `backend/auto_voucher/server.py:128`

```python
threading.Thread(target=run, name=job_id, daemon=True).start()
```

**问题**: Daemon 线程在 Python 进程退出时被强制终止：
- SQLite WAL 写入可能不完整
- 归档文件可能处于半写入状态
- 正在执行的重命名操作可能留下 `.tmp` 文件

**风险等级**: 低（本地应用，SQLite WAL 通常能自恢复），但设计上不够健壮。

**建议修复**: 在 `main()` 的 `finally` 块中增加等待后台任务完成的逻辑（设置超时）：
```python
finally:
    # 等待后台任务完成（最多 5 秒）
    active = jobs.status().get("activeCount", 0)
    if active:
        print(f"等待 {active} 个后台任务完成...")
        time.sleep(5)
    server.server_close()
```

### 12. `ConfiguredFinanceConnector._request` 不支持 GET 请求参数 — `backend/auto_voucher/connectors.py:638-659`

|------|----------|
| **导入幂等** | SHA-256 内容哈希去重，重复文件不创建第二份资料 |

## 总体评价

Auto Voucher 是一个**质量很高的本地优先财务应用**。安全设计（密钥隔离、审计只追加、自动脱敏、Ed25519 签名验证）和完整性保证（SHA-256 去重、借贷强制校验、备份校验、原子写入）做得非常扎实，在同类本地应用中属于第一梯队。

代码总量约 10,000 行（含测试），结构清晰，六层闭环设计合理。CI 流水线完整（密钥扫描 → 测试 → 构建 → 审计 → 发布 → 读回校验）。Docker 更新机制（镜像摘要、健康检查、数据卷保留和失败回退）满足当前交付边界。

主要改进方向：
1. **前后端数据模型一致性**（OCR 创建事项路径）
2. **前端单体文件拆分**（随功能增长的必要重构）
3. **守护线程优雅关闭**（增强鲁棒性）
4. **几个边界条件的防御性处理**

建议在 v0.3.0 中优先处理 Critical 和 High 级别问题，Low 级别可在后续迭代中逐步优化。
